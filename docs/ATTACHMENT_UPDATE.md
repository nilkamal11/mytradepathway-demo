# Attachment requirements and implementation

The public demo keeps the existing MyTradePathway design and browser-only architecture. The update uses the supplied trade JSON, all eight rendered pages of the v3 developer specification, and both use-case documents. The sender's HTML implementation and styles are excluded at the user's direction. No attachment scripts were executed. The email, archive, PDF, Word files and private correspondence are not part of this repository.

## Scope and content

The JSON contains ten trades, twelve local-program records (two additional DuPage records), 135 original questions and 58 deduplicated links across the program records. These are **supplied, unverified reference content**. The receipt date is October 3, 2026; this is not a verification date. Provider data is rendered as text and safe HTTP/HTTPS links, with no imported HTML, scripts, styles, inline handlers or private direct-conversation attribution. Composite quotations were omitted rather than presented as testimonials.

All people, school identities, activity and access grants remain synthetic. Eleven earlier synthetic programs are retained and labelled as demonstration pathways so existing browser progress and edits retain their stable IDs. New trade visits default to the supplied local program; legacy choices remain available below it. State schema v2 upgrades the prior v1 snapshot under the same storage key and adds reference records without replacing old user activity, program edits, grants or progress.

## Explicit assumptions and unresolved source conflicts

- The JSON is the available structured content source when the prose spec says nine trades but the export contains ten.
- The spec mentions a third DuPage carpenter sub-object, but the JSON does not contain one. The carpenter text mentions Local 1889; a separate application roadmap is not supplied and is not invented.
- Match scores are the percentage of selected preferences appearing among the supplied trade tags, with stable alphabetical tie-breaking. They are not admission probabilities, validated psychometrics, wage rankings or statements of physical suitability.
- Checklist boundaries use `checklistCutoff`; each recommended dashboard item is stored separately. Post-acceptance roadmap steps do not count toward preparation progress.
- Separate track comparisons do not imply every track has the same entrance process. The supplied Welder content describes multiple locals and asks applicants to confirm the relevant selection process.
- Provider deadlines are snapshot text, not a live calendar. The DuPage electrician application window in the export ended September 30, 2026, before this update; its text is retained as reference history with a visible closed-window warning.
- Named school outreach contacts and quotes from direct conversations were not independently verified. The demo uses public office lines and omits personal quotations.
- Real sign-up, email verification, Google/Microsoft OAuth, Stripe Checkout/webhooks, backend storage, SIP2/ILS card+PIN validation, staff approval, production analytics, AI extraction and public document uploads are not implemented in this static public demo. Earlier private production groundwork remains separate.
- Payment cadence, library integration sequence, the final paywall, retention, transfers/refunds, school privacy terms and client-owned domain/email/hosting setup remain production decisions. No paid services, new credentials or third-party messages were created.

## Validation and review

Run `npm test`, `npm run build` and `npm run test:e2e`. Twenty state/domain tests cover old journeys, v1 migration, retained progress, grouped tags, county isolation, content safety and versioned edits. Ten browser journeys cover the original flows plus supplied roadmaps, assessment editing, practice review, learning directories, expanded admin editing and offline shell reload. Browser checks use isolated profiles and assert responsive widths; generated screenshots and test logs are ignored.

The GitHub Pages workflow repeats state/build and Chromium journey checks at the exact pushed commit before deployment. Live deployment is then checked with the same journeys in isolated Edge using `LIVE_DEMO_URL`.
